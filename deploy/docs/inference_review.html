1. 方案总览

核心取舍只有一条：ONNX 是唯一跨机器传递的产物，引擎不是。 TensorRT 的 .plan 文件把 TensorRT 版本、GPU 架构和驱动一起烧进去了， 开发机上生成的引擎在 Orin NX 上根本不会加载。所以引擎构建必须发生在机器人上， 这直接决定了工作区要提供的是「一套能在两种机器上都跑起来的工具」，而不是一个编译产物。

开发机 训练 → ONNX rsl_rl 导出 policy.onnx：4×Gemm + 3×Elu，425→24，无归一化层
开发机 接口契约 dump_interface.py 从活的 Isaac Lab 环境导出关节顺序、观测布局、动作缩放
开发机 参考数据 make_fixture.py 用 PyTorch 跑 512 个样本，记录输入输出作为金标准
机器人 构建引擎 r1_build_engine 在目标机上把 ONNX 编译成 .plan
机器人 对齐验证 · 闸门 r1_parity_check 回放金标准，比对数值并剖析时延
机器人 ROS 2 节点 r1_policy_node 维护 5 帧历史、推理、发布动作与关节目标

职责切分

节点只做三件事：堆历史、推理、发指令。它订阅的是当前这一帧的 85 个浮点数， 而不是拼好的 425 维向量。这条边界是刻意划的 —— 425 维的排布方式是训练时的产物， 每多一个自己拼装它的消费者，就多一次静默拼错的机会。

话题类型维度说明
~/obsFloat32MultiArray85订阅。当前帧传感器值，按观测项顺序排列
~/actionFloat32MultiArray24发布。策略原始输出
~/joint_targetFloat32MultiArray24发布。default + scale × action，可直接送 PD
~/latency_usFloat321发布。单周期推理耗时，便于 rosbag 事后核查

另有 mode:=selftest：节点用内部定时器以 50 Hz 自驱、喂合成观测， 不需要机器人也不需要仿真。这是给 W06「悬空空跑」提前排练用的。

2. 两个改变做法的发现

发现一 · 部署阻断级

TensorRT 10.3.0 在这台机器上静默算错

我最初选的就是 10.3.0 —— JetPack 6.1/6.2 给 Orin 配的版本， 与目标一致本是最稳的选择。它在这台机器（Turing sm_75，驱动 580.173）上构建出的引擎 能加载、满速运行、不报任何错，但返回的数字是错的：与 PyTorch 相差 max_abs 3.0e+01， 即输出与正确答案毫无关系。

这不是精度问题，也不是 tactic 选择问题。从 ONNX 解析器和从 TensorRT API 手工搭网络， builder 优化等级 0–5 全试，FP32/FP16 都试，C++ 和 Python 两条路径 —— 结果完全相同； 而 onnxruntime 与 PyTorch 彼此吻合到 1e-5。逐层二分的规律很具体： 含两个 ELU 的子图正确，含三个就错。

换 TensorRT 10.7.0，与 PyTorch 对齐到 1.05e-05。setup.sh 已锁定该版本。

真正重要的是它的推论。开发机和机器人现在处在不同的 TensorRT 版本上， 而这个故障没有任何外部征兆 —— 不抛异常、不打警告、满速运行、输出量级看着完全正常。 唯一能发现它的手段是拿外部参考做数值比对。所以：

因此成为硬性流程

r1_parity_check 必须在机器人上、对机器人上构建的引擎、再跑一遍， 然后才允许策略驱动任何一个关节。开发机上的绿灯对 Jetson 没有任何保证。

这与 Week04 的执行器力矩超限、头部顶死硬限位属于同一类： 没有任何聚合指标会报警，只能靠与外部参照物比对才能发现。区别在于前两个的代价是「策略不可部署」， 这一个的代价是「策略在真机上做布朗运动」。

发现二 · 微基准把推理速度高估了 8 倍

测量方式p50p95p99max
紧凑循环（r1_parity_check，2000 次）23.6 µs24.7 µs43.5 µs387 µs
50 Hz 占空比（r1_policy_node）198 µs230 µs386 µs464 µs

同一个引擎、同一台机器。控制回路每 20 ms 只做约 24 µs 的活，远不足以把 GPU 从空闲档拉出来： nvidia-smi 显示 persistence mode 关闭、pstate P8、 SM 时钟 450 MHz，而上限是 2100 MHz。紧凑循环让 GPU 一直保持高频， 测的是真实系统从不处于的工况。

两个数字对 20 ms 预算都很宽裕（诚实的那个约占 1%），但汇报要用 50 Hz 那一列。 Orin 上对应的旋钮是 nvpmodel 与 jetson_clocks，必须先设好再谈时延。

对 W08 的推论：batch=1 下这个模型的时延由 kernel 启动开销主导，不由算术主导 —— FP16 引擎在这里产出了与 FP32 逐位相同的结果，因为 TensorRT 判定 FP32 内核更快、 根本没启用 FP16。所以 INT8 量化能省的是显存和功耗，不是毫秒。

3. 部署接口契约

这些数字都不在 ONNX 里 —— ONNX 只知道「425 进、24 出」。任何一项弄错， 结果都是策略满速运行然后走进地板，所以它们由 dump_interface.py 从活环境导出，而不是手抄。

观测：425 = 5 帧 × 85，按项展平

这是整条链路里最容易静默出错的一处。正确布局是项优先：

[ang_vel ×5][gravity ×5][command ×5][joint_pos ×5][joint_vel ×5][action ×5]
    15          15           15           130            130          120     = 425

而不是五个连续的 85 维帧。两种排法长度都是 425，所以错的那种照样加载、照样运行、 照样输出一个看起来很自信的结果。每项内部最旧的帧在前。 ObsAssembler 独占这段逻辑，单元测试既断言正确布局、也显式断言不等于帧优先布局。

观测项每帧宽度×5偏移

注意 joint_pos / joint_vel 是 26 维，覆盖全部关节 包括策略不驱动的两个头部关节；动作是 24 维。两个向量的索引 i 指向不同关节。

动作：24 维，articulation 顺序

顺序是机器人运动树的广度优先序，不是选中它们的正则表达式的顺序 —— waist_roll_joint 排在索引 2，夹在两个 hip_pitch 和两个 hip_roll 之间。 从 interface/policy_interface.md 读，不要凭印象重打。 

q_target[i] = default_pos[i] + scale[i] × action[i]

5. 四项决策（已确认）

2026-08-19 确认，四份文档已同步更新。

① TensorRT 版本 —— 不预设，实测说了算

已产出 《R1 真机上机操作清单 · 推理链路》（~/kdw/）：七个阶段， 阶段 4「数值对齐」是硬闸门，含失败时的五选项决策树 —— 降精度重建 / 拆图规避 / onnxruntime 兜底 / 手写 CPU 前向 / 升级 JetPack，按代价从低到高。

值得单记一笔：这个策略只有 4 个 GEMM + 3 个 ELU、约 90k MAC，Orin 的 ARM 核心几十 µs 就能算完。 即使 TensorRT 整条路都走不通，推理本身也不构成风险 —— 真正的代价是项目的 TensorRT 叙事（FR-Q*）需要重写。清单末尾一句话总结：先证明它算得对，再关心它跑得快，最后才让它碰关节。

② 观测来源 —— 保持通用话题 + 单独 bridge

策略节点继续订阅通用 Float32MultiArray，由独立 bridge 负责 unitree_hg/LowState → 85 维帧的转换。已写入 Week06 计划步骤 2。（2026-08-26 上机核实：R1 用 unitree_hg，此前的 unitree_go 是四足的包。）

多一跳在 20 ms 预算里可以忽略；换来的是节点可单测、可 rosbag 回放、可被仿真直接驱动。

③ W08 的 INT8 目标 —— 改为「行为不退化」

Week08 计划已改：新增「INT8 行为一致性验收」为独立步骤，分三层 —— 单步数值给解释、闭环轨迹给硬判据、真机悬空给安全，只有第二层是通过线。 原「相对加速比达标」目标撤销；基准脚本重点从时延转向体积与功耗。

同时加了一条风险提示：不要为了让 INT8「有收益」而改成吞吐量口径去凑加速比。 真机就是 batch=1、50 Hz，换口径测出的数与部署现实无关，评审时会被问穿。 如实说「时延无差异」反而把 INT8 重新定位成 M3 鲁棒性实验的可控扰动源，与 FR-R2/PG-5 直接接上。

④ 超时看门狗 —— 加入 Week06

新增目标与独立步骤：三类异常（观测断流 / 推理失败 / 频率跌落）各有检测与降级； 降级行为的三个候选必须在该周选定一个写进文档；测试要主动制造故障（杀 bridge、发畸形帧、拔网线）。

恢复必须显式：跨越空白期的 5 帧历史属于训练分布外，要清空缓冲、重填满再输出 （ObsAssembler::Reset() + hold_until_warm 已支持）。 计划里明确标注看门狗不在「高风险周可砍」范围内。 在它到位之前，任何真机测试必须留人在急停开关上。
